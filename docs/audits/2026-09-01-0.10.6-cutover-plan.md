# 0.10.6 cutover plan

Date: 2026-09-01.

Re-scopes the 0.10.6 milestone to the foundation only, and sequences it so
`dimm-city/gutterpress` and `dimm-city/dc-op-manual` land in one window without
freezing the book. **This supersedes the phase lists in the two tracking issues**
(gutterpress#248, dc-op-manual#48).

Backing documents: `2026-09-01-css-architecture-review.md`,
`2026-09-01-extensions-review.md`.

---

## TLDR

The drift risk is real but narrower than it looks, and it is beatable by one
discipline: **the mechanical half of the cutover is a script, not a branch.** A
branch rots against 14 commits a day. A script does not care what landed while it
was being written — you re-run it at cutover time against whatever `main` is.

Result: **~9 working days, with the freeze on `dc-design-guide/css/**` lasting
60–90 minutes.**

---

## 1. What the constraint actually is

Measured against `dc-op-manual@main` on 2026-09-01, last 30 days:

| Measure | Value |
|---|---|
| Commits in 30 days | **430** (~14/day) |
| Commits touching field-guide markdown | **383** |
| Commits touching `dc-design-guide/css/` | **39** (~1.3/day) |
| …of those, also touching markdown | **20** |
| Books consuming the shared CSS | **2** |
| Lines coupling the two repos | **1** |

Three facts shape everything below.

**The blast radius is two books, not six.** Only `field-guide/manifest.yaml`
references `../dc-design-guide/css/`; the design guide itself uses
`css/index.css`. SysOps, dc-rules, pc-sheet, KickStarter and monsters-manual all
carry independent stylesheets and are untouched by the entire CSS cutover.

**The repos are coupled by one line.** `dc-op-manual/package.json` pins
`"gutterpress": "0.10.2"` — two releases behind current. "Landing together"
means: publish core, then one PR in the book repo bumps the pin *and* lands the
CSS surgery. Revert that PR and the pin reverts with it.

**A CSS-only freeze is not free.** Half the CSS commits also touch markdown, so
"don't touch CSS" blocks real work. Any plan whose safety depends on a multi-day
freeze will slip or be ignored. The plan must need a freeze measured in hours.

## 2. Strategy: four decisions

### 1. Core 0.10.6 is a no-op for the un-migrated book

Every core change ships additive: new `gp-` utilities nothing yet uses, a new
warning, `@layer` wrapping around core's own two blocks (unlayered author CSS
still beats layered core CSS at any specificity), and adopted print fixes at
`:where()` zero specificity that the book's existing rules already override.

**The release gate for core is a zero-diff render of the current, unmigrated
field guide.** That is what makes shipping both halves on the same day safe
rather than brave — if the book PR slips a week, core is already in production
doing nothing visible.

### 2. Split the book work by conflict profile, not by topic

- **Judgment work** — deleting dead rules, fixing comments, moving three token
  blocks to `:root`, consolidating the `.section` chrome escape. Small diffs,
  real decisions. These land as **ordinary small PRs, early, unfrozen**. A
  40-line diff merges fine against 14 commits a day.
- **Mechanical surgery** — splitting `dc-components.css` into families,
  splitting `dc-tokens.css`, moving columns to their components, re-cutting the
  override files, adopting layers. Whole-file rewrites that conflict with
  everything. These are written **as a transformation script** and executed
  once, at cutover.

### 3. The mechanical half is a script, not a branch

This is the answer to "op manual is very active and will drift quickly". A
long-lived re-cut branch accumulates rebase debt every day it exists. A script —
`tools/recut-css.mjs` in the book repo, idempotent, operating on named rule
blocks rather than line numbers — has no rebase debt at all. It is developed
against a snapshot, dry-run nightly against live `main`, and on cutover day it
runs against whatever `main` is at that moment.

**Drift stops being a schedule risk and becomes a nightly signal.**

### 4. Nothing in 0.10.6 touches markdown

Markdown is where 383 of the 430 commits live. Every item that would require
editing a manuscript is deferred or shimmed: the `.pmd-*` → `gp-` migration keeps
`.pmd-*` as aliases; the prefix normalization ships CSS-side with old names
aliased and the markdown rename moves to 0.10.7; the two inert-class deletions
are the only markdown edits and are two single-line removals landed as ordinary
PRs.

## 3. Step zero: the parity gate

Everything above depends on answering "did that change the book?" in minutes
rather than by eye. That harness does not exist as a repeatable script today —
the August audit did it by hand, and a `dc-design-guide/baseline/gallery/` tree
existed at one point and was deleted. Rebuild it first.

The primitives are already in core. `packages/cli/src/lib/pdf-inspect.ts` exposes
`loadPdf`, `getPageSize`, `getTextPass` (text runs with extents) and `getOpPass`
(image placements per page). A parity gate needs no new dependency and no
rasterization:

```
tools/render-parity.mjs <baseline.pdf> <candidate.pdf>

  compares, per page:
    page count            exact
    page size             exact
    text run extents      ±0.5pt, plus exact string content
    image placements      ±0.5pt on x/y/w/h
  exit 1 on any mismatch; prints page, kind, before → after

  --waive waivers.json    intentional diffs, each with a one-line reason
```

Two consumers:

- **gutterpress CI** — build the field guide with the previous release and with
  the PR's build; any diff fails. This enforces "core 0.10.6 is a no-op".
- **dc-op-manual CI** — build both affected books before and after; the re-cut
  script's every step must come out clean or carry a reviewed waiver.

The gate is *stronger* than a raster diff for this job: it catches a paragraph
that reflowed by half a point on page 240, which a downsampled pixel comparison
misses, and it never flags an anti-aliasing difference. Keep a rasterized
spot-check for the handful of pages carrying pinned or bleed art.

## 5. The schedule

Two tracks run in parallel and meet on cutover day. Day numbers are working days
from kickoff; the *order* is what matters, not the calendar.

### Stage 0 — Build the gate (days 1–2, both repos, no freeze)

- `tools/render-parity.mjs` in gutterpress, over `pdf-inspect`.
- Capture baselines: field guide and design guide, built with the pinned 0.10.2
  CLI, committed as the reference.
- Wire it into both repos' CI as a required check.

**Gate:** the gate reproduces a known-good build twice with a byte-identical
report. Until that is true, nothing else starts.

### Track A — Core, shipped as a no-op (days 2–6, gutterpress, no freeze)

1. **#227 @layer.** One layer per existing sheet, declared in current load order,
   engine styles left unlayered. This makes adoption provably order-preserving:
   with one file per layer, within-layer ordering cannot matter.

   ```css
   @layer gp.marker, gp.vocab;      /* core, injected first  */
   /* book sheets, declared by the manifest in load order:  */
   @layer dc.tokens, dc.base, dc.components,
          dc.templates, dc.pages, dc.guide, book;
   /* engineStyles.native stays UNLAYERED — still wins everything */
   ```

2. **#225 / #228** vocabulary, with `.pmd-no-break`, `.pmd-break-before`,
   `.pmd-col-span` kept as aliases so no book has to change markdown.
3. **#231** print-fix adoption at `:where()`.
4. **#226** unknown-class warning; **#229 #230** doc fixes.

**Gate:** every PR — the parity gate against the *current, unmigrated* field
guide must be clean. A single diff means core is not a no-op and the change needs
rescoping.

### Track B1 — Judgment work, as ordinary PRs (days 2–7, dc-op-manual, no freeze)

Six small PRs (#32, #33, #34, #35, #38, #39), each gated, each landing normally
alongside daily book work. Order matters in one place: **#34 before #38**, so the
specialty collapse has one token convention to wire into.

**Gate:** each PR clean, or carrying a reviewed waiver. #39 (`.dc-plain`) is the
one expected to need waivers — record each intentional pixel with a reason.

### Track B2 — Write the re-cut script (days 3–8, dc-op-manual, no freeze)

- `tools/recut-css.mjs`: idempotent, block-addressed (find rules by selector, not
  by line), and it **fails loudly** if a block it expects is missing or ambiguous
  — that failure is the drift alarm.
- Run it nightly in CI against live `main`: apply → build → parity gate. A red
  night means someone edited a block the script moves; fix the script that
  morning, not on cutover day.
- Scope: #41 columns co-location, #43 file splits, #36/#45/#37 the override and
  engine re-cut. It also rewrites `field-guide/manifest.yaml`'s `styles:` block
  and the `@layer` declarations to match the new file set.

**Gate:** three consecutive green nightly runs against a moving `main`. That is
the release criterion for the script — it proves the transformation is stable
under drift, which is exactly the property the calendar is threatening.

### Cutover (day 9) — the only synchronized moment

Expected wall-clock: **2–4 hours**, of which the CSS freeze is roughly **60–90
minutes**.

### Settle (days 10–12, no freeze)

- Watch a full `build:all` and a PDF/X build of the field guide
  (`field-guide/pdfx.sh`) — the print path is the one consumer the parity gate
  does not fully model.
- Update `dc-design-guide/docs/css-architecture.md` to describe the new file set;
  it currently documents the old one in a table.
- Tag `0.10.6`, publish, close both milestones.

## 6. Cutover-day runbook

| # | Step | Owner | Freeze? |
|---|---|---|---|
| 1 | Confirm last night's script run was green and Track A is merged. If either is red, **stop — reschedule**. There is no partial cutover. | both | no |
| 2 | Publish `gutterpress@0.10.6` to npm. | core | no |
| 3 | Announce freeze on `dc-design-guide/css/**` and `field-guide/manifest.yaml`. Markdown stays open — authors keep working. | book | **starts** |
| 4 | Branch from current `main`. Run `tools/recut-css.mjs`. Bump the pin to `0.10.6` in the same commit range. | book | yes |
| 5 | Build field guide + design guide. Run the parity gate against the day's baseline. | book | yes |
| 6 | Read the report. Clean, or every diff matches a pre-agreed waiver → merge. Anything unexpected → **abort, unfreeze, diagnose off the critical path**. | book | yes |
| 7 | Unfreeze. Post the new file map to the team. | book | **ends** |
| 8 | Re-baseline: the post-cutover build becomes the new reference. | book | no |

Step 6 is the whole plan in one line. Because every prior step was individually
gated, the cutover report should be empty — if it is not, the correct move is to
abort rather than to reason about it under a freeze.

## 7. Rollback and failure modes

### Rollback

Revert the single book-repo PR. It carries the CSS surgery *and* the version-pin
bump together, so reverting restores both the old file layout and the old CLI in
one operation, with no coordination against the npm release. Core 0.10.6 stays
published and keeps doing nothing, exactly as before the book adopted it.

### The four ways this goes wrong

| Failure | Detected by | Response |
|---|---|---|
| Someone edits a block the script moves | nightly dry run goes red | Fix the script that morning. This is the expected case — ~1.3 CSS commits/day means it *will* happen. |
| `@layer` shifts something in Chromium print | Track A parity gate, day 2–3 | Caught a week early, against the unmigrated book, with the cutover still unscheduled. |
| Core 0.10.6 is not actually a no-op | Track A gate | Rescope the offending change. Non-negotiable — this property is what makes same-day landing safe. |
| The book is mid-print-run at cutover | calendar, not tooling | Do not cut over inside a print window. The PDF/X path has verification the parity gate does not model. |

### If it slips

The minimum viable cutover — the part that must land together — is **#227 + #225
+ #231** in core and **#41 + #43 + #36/#45/#37** in the book. The six judgment
PRs are independently valuable and can land before or after. If the window
compresses, drop #38 and #39 first: they are the largest judgment items and the
only ones expected to produce waivers.
