# Gutterpress 0.11.0 release notes

This release adds a source-first rich-editing surface — shared by the
desktop app and a new, Experimental VS Code extension — and, alongside it,
removes a substantial amount of architecture the new design made
redundant: in-preview editing, a dormant browser-app implementation inside
the desktop package, a broad platform service locator, and Electron's
second (HTTP) transport. See `CHANGELOG.md` for the user-facing summary;
this document has the fuller picture, including what was deleted and what
is honestly still open.

Full history: `docs/plans/source-first-editor-enterprise-refactor.md` and
its run specifications (`docs/plans/source-first-editor/runs/`). Every
binding decision has an ADR at `docs/adr/0012`–`0017`. The architecture as
it now stands is described in
`docs/architecture/source-first-editor.md`.

## What shipped

- **A source-first rich editor**, built once
  (`@dimm-city/gutterpress-editor`) and mounted identically by the desktop
  app and the VS Code extension. Exact Markdown source remains the only
  authoritative document at all times — opening, closing, and switching
  between Source and Rich mode changes zero bytes; an accepted edit changes
  only the exact range it touched. See `docs/adr/0012-source-first-editor-sparse-projection.md`.
- **The desktop app's Edit pane gained a Rich mode** alongside the existing
  CodeMirror Source mode, switchable per document, sharing the same
  document session, autosave, and recovery behavior either way. Rich mode
  covers ordinary Markdown authoring (headings, lists, blockquotes,
  emphasis, links, images, tables, code) plus Gutterpress-specific
  authoring: layout markers render as recognizable chips instead of raw
  `@` syntax, and project-plugin regions render through the plugin's own
  output, with a two-state (inactive/active) design and a source-mode
  fallback wherever the editor cannot prove a region is safely editable.
- **A new, Experimental VS Code extension**, `@dimm-city/gutterpress-vscode`
  (published separately from `gutterpress`). It registers an optional
  custom text editor — never the default for `.md` files — built on the
  same shared editor package, with Build/Preview/Open Source commands and
  workspace-trust-gated plugin execution. See `docs/vscode-extension.md`.
  Because `@vscode/markdown-editor` has no generic hook for a custom block
  view, the extension's rich surface runs on a small internal fork,
  `packages/vscode-markdown-editor` — two patches, ten hunks against the
  pinned upstream version, documented hunk-by-hunk with a removal trigger
  in `PATCHES.md`. See `docs/adr/0014-shared-editor-package-and-fork.md`.
- **A new public subpath export, `gutterpress/plugins`**, giving any host —
  the VS Code extension, and the desktop app itself — the same plugin
  loader the CLI's own build and preview pipeline uses, rather than each
  host maintaining its own narrower copy (the desktop previously did
  exactly that, and was switched over). `gutterpress` and `gutterpress/api`
  are unchanged; `gutterpress/render` gained the projection surface the
  shared editor consumes (`createEditorProjection`, `PROJECTION_SCHEMA_VERSION`,
  `inlineSourceMetaOf`, `sourceTokenOccurrenceAt` and their types) — the
  full exports contract is pinned by
  `packages/cli/tests/integration/package-exports.test.ts`.
- **The paginated preview is now read-only.** In-preview editing (the
  click-to-edit block overlay, the context menu's mutating actions) is
  gone; navigation, selection/copy, opening a link or image, diagnostics,
  and page controls remain exactly as before. The preview stays the
  print/layout authority — `packages/cli/scripts/native-parity-gate.ts`
  (`parity:gate`) is the CI-wired gate that must stay green with an empty
  allowlist. It could not be executed in this program's sandbox (Chromium
  148+ required; the sandbox has 141.0.7390.37) — no run of this gate is
  recorded in this program's evidence; see `p7-sweeps.md` §1.1 for the
  attempted run.
- **The desktop app is one process.** Electron previously ran a local
  loopback HTTP server (with its own bearer-token authentication) alongside
  its IPC bridge; that server, the token, and the proxy in front of it are
  deleted. The packaged app now serves its own interface directly off disk
  via a custom `app://` protocol handler, and every host operation crosses
  one runtime-validated IPC boundary (~120 `secureHandle` channels across
  26 registrar modules) instead of being split across two transports. See
  `docs/adr/0016-electron-single-ipc-transport.md`.
- **The dormant desktop PWA implementation is deleted**, not finished. It
  was never a shipped capability — an in-browser folder-open path,
  in-browser preview, and IndexedDB persistence, dormant since it was
  first scaffolded. A future browser product, if built, is its own package
  consuming the same shared editor and rendering libraries this release
  introduces, not a mode hidden inside `packages/desktop`. See
  `docs/adr/0015-future-web-product-is-a-separate-package.md`.
- **The broad `Platform`/`HostServices` locator is gone**, replaced by
  narrow, feature-owned capability modules (one per bounded context —
  files, project config, remote/sync, publishing, VCS, recovery, updates,
  lint, doctor, app lifecycle, editor host, build/export) over one shared
  bridge accessor. See `docs/adr/0017-narrow-feature-owned-capabilities.md`.

## What was deleted

The deletion ledger (`docs/plans/source-first-editor/deletion-ledger.md`)
carries the exact, re-derivable figures for every phase; the headline
checkpoint numbers, cited from there and from the run specifications, are:

- **P4 — preview editing and its mutation machinery**: net **−6,719 LOC**.
  `InlineEditController`, `CommitEngine`, the preview's image/link source
  rewriters, and the in-flow `contenteditable` authoring path are gone; the
  preview bridge protocol moved v8→v9 (five mutation message types removed).
- **P5a — the dormant PWA implementation**: net **−2,546 LOC** (19
  production+test files, +92/−2,638, `git diff c33868f8..5db8c581`).
  `WebAdapter` (901 lines), `web-fs`/`web-store` (446 lines combined), the
  FSA type declarations, the service-worker path, four now-orphaned test
  suites, and the duplicate static viewer bundle are all deleted.
- **P5 overall (P5a's review-repair rounds onward through P5d — the
  Platform-locator replacement, all four HTTP-to-IPC migration subruns, and
  the local server deletion)**: 313 files touched, **net −3,621 LOC**
  (+11,177/−14,798). Desktop HTTP routes: 104 → 0. IPC handlers: 12 → 120.
- **P6 — composition-root slimming and export/ADR records**: 56 files,
  +3,887/−1,008. This phase is not primarily a deletion phase — most of the
  addition is new ADRs, ownership docs, and export/registration tests — but
  both composition roots shrank: `+page.svelte` 4,739 → 4,543 lines,
  `electron/main.ts` 2,188 → 1,965 lines, with the extracted responsibility
  landing in feature-owned controllers and registrar modules instead of
  disappearing.

The final combined net-production-LOC figure across the P4–P6 simplification
phases, and the remaining seven ledger metrics (module/file count,
dependency count, platform method count, IPC handler count, preview
protocol message count, architecture-check count), are this same P7 run's
Lane A deliverable — see `deletion-ledger.md`'s final section for the
complete, re-derived numbers.

## Known limitations

Carried honestly, not glossed over:

- **The D13 performance budget is not met.** The plan's target: repeated
  ordinary typing in a 250 KiB document keeps p95 edit-to-paint under
  100 ms after warm-up, on the project's CI reference runner. Measured in
  this sandbox (not the CI reference runner): 25 KiB is within budget;
  250 KiB p95 is **~545–632 ms**, 1 MiB p95 is **~2.3 s**. The cost is
  inside the vendored `@vscode/markdown-editor` fork and scales with
  document size — root-caused to the fork's whole-document geometry
  remeasurement on edit. A sound fix (Patch 2, `SFE-P3f`) is already
  vendored and helps end-of-document typing, but the benchmark's own
  navigation defect means mid-document typing — the case the budget is
  meant to cover — isn't yet measuring the improved path. Three ordered
  follow-ups are recorded in `packages/vscode-markdown-editor/PATCHES.md`
  and the SFE-P3f close-out: fix the benchmark's navigation defect;
  implement the delta-translation variant so mid-document typing also
  reuses cached geometry; then re-profile the remaining residual (an
  EditContext input-path cost that is located but not yet proven as the
  cause). Rich mode remains fully usable for ordinary chapter-length
  documents; this budget governs sustained typing in large (250 KiB+)
  files specifically.
- **Two accessibility gaps are open.** The rich-editing surface has no ARIA
  landmark role anywhere in its stack, and the desktop shell has no
  `<main>` landmark or skip-link. Recorded by the P3d accessibility review
  as open items for a follow-up release, not fixed in this one.
- **Three interaction shapes are deliberately not implemented, not
  missing by accident**: paste into the rich editor is plain-text-only (no
  rich-paste formatting yet); block movement has no pointer-drag path
  (keyboard-driven move commands exist); there is no slash-command menu in
  Rich mode outside the desktop's existing toolbar. These were evaluated
  and pinned as acceptable for `0.11.0`'s Experimental release rather than
  deferred by omission.
- **A few plugin-heavy layouts fail closed to source-only editing in Rich
  mode** rather than offering rich editing: an image or link inside a GFM
  table cell with an escaped `|` refuses editing for the whole row, and an
  image inside a raw HTML block refuses. Both are intentional fail-closed
  behavior (an ambiguous case falls back to source rather than guessing),
  not silent data loss.
- **Real-VS-Code activation is a recorded deviation, not a gap in the
  extension itself.** A bounded `@vscode/test-electron` attempt was made
  and failed on a network policy denial in this sandbox (`downloadAndUnzipVSCode`
  cannot reach `update.code.visualstudio.com`; exact command and failure
  recorded in `docs/plans/source-first-editor/runs/SFE-P3c.md`'s
  "Deviations and evidence" section), and the resulting dead launcher
  scaffold was removed rather than left in the tree unused. The extension's
  evidence for this release is its harness test suite (228 unit + 34
  browser tests, run against a fidelity mock —
  `packages/vscode-extension/tests/support/fidelity-vscode.ts` — with real
  `TextDocument`/`WorkspaceEdit` semantics computed from actual text
  content, not hand-written per-test return values) plus a real-Node
  module-load test proving the built `dist/extension.js` actually loads
  (an earlier build did not: bundling `gutterpress` in dragged a
  CJS-incompatible import along with it). The first environment with
  network access to the VS Code download host should run a real
  `@vscode/test-electron` pass before this extension moves past
  Experimental.
- **Packaged-asar smoke: closed this release.** Every prior run's
  packaged-build evidence ran Electron **unpackaged** (`out/main/main.js`
  directly, `app.isPackaged === false`), with the asar-serving code path in
  `electron/app-protocol.ts` proven only by a unit test stubbing
  `process.resourcesPath`. The P7 sweep
  (`docs/plans/source-first-editor/p7-sweeps.md`) drove the real thing: an
  `electron-builder --linux dir` build produced `app.asar` (8,856 entries;
  renderer build, main, and preload all inside, zero server-bundle
  markers), and the packaged binary launched headlessly to first paint with
  the renderer served over `app://` from the asar and no fatal log lines.
  Windows/macOS packaged smokes remain CI-runner work.

## Upgrade notes

- **Breaking, user-visible: editing directly in the preview is gone.**
  Anything you used to do by right-clicking or double-clicking a block in
  the preview — including changing an image's or link's properties — now
  happens in the Source or Rich editor. Both editors now cover strictly
  more than the preview's old context menu did (updating an *existing*
  image or link's properties was previously only possible from the
  preview; it is now a command in both editors). Preview navigation,
  click-to-source, selection/copy, and opening a link or image are
  unchanged.
- **No project file format, manifest, CLI, build, or publish behavior
  changes in this release.** Everything above is editor and desktop-app
  architecture; a project that built and previewed correctly under 0.10.2
  builds and previews identically under 0.11.0. The public `gutterpress`
  and `gutterpress/api` exports are unchanged; `gutterpress/render` gained
  the projection surface the shared editor consumes (`createEditorProjection`,
  `PROJECTION_SCHEMA_VERSION`, `inlineSourceMetaOf`, `sourceTokenOccurrenceAt`
  and their types). The markdown-it plugin API contract for plugin authors
  is unchanged (plugins
  remain ordinary `(md, options) => void` markdown-it plugins — no new
  Gutterpress-specific plugin API was introduced for rich-mode support).
- **`@dimm-city/gutterpress-editor` and the VS Code extension are
  Experimental for `0.11.0`.** Their identifiers, commands, and internal
  contracts may change without the deprecation cycle a stable Gutterpress
  surface would owe you. If you don't use Rich mode or the VS Code
  extension, nothing in your workflow changes.
- **No user-data migration.** Nothing about your project's files, version
  history, or sync state changes as part of upgrading.
