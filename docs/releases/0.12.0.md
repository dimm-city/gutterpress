# Gutterpress 0.12.0 release notes

This release adds a source-first rich-editing surface — shared by the
desktop app and a new, Experimental VS Code extension — and, alongside it,
removes a substantial amount of architecture the new design made
redundant: in-preview editing, a dormant browser-app implementation inside
the desktop package, a broad platform service locator, and Electron's
second (HTTP) transport. See `CHANGELOG.md` for the user-facing summary;
this document has the fuller picture, including what was deleted and what
is honestly still open.

Full history: `docs/plans/source-first-editor-enterprise-refactor.md` and
its run specifications (`docs/plans/source-first-editor/runs/`). Every
binding decision has an ADR at `docs/adr/0012`–`0017`. The architecture as
it now stands is described in
`docs/architecture/source-first-editor.md`.

## What shipped

- **Edit on the page.** In Read, an author sees a lock pill over the
  pages. Locked is the preview as it prints — the print path's own pages,
  unchanged. Unlocking lays the paged editor over the pane: the book laid
  out by the same engine, every chapter mounted in book order, edited in
  place. Exact Markdown source remains the only authoritative document at
  all times — locking, unlocking and switching between Edit and Read change
  zero bytes; an accepted edit changes only the exact range it touched
  (`docs/adr/0012-source-first-editor-sparse-projection.md`). Edits write
  through each chapter's own buffer, so autosave, snapshots and
  external-change reconciliation behave as they do in Edit. The formatting
  bar, Insert menu, image properties and snippets work on the page;
  right-click offers Image properties, Reveal in Media panel, Copy, Edit in
  source and Lock. Read opens locked every time; a reader (Settings → App)
  never sees the pill; Edit mode and its preview are untouched.
- **A source-first rich editor**, built once
  (`@dimm-city/gutterpress-editor`) and mounted identically by the desktop
  app and the VS Code extension. The paged editor covers ordinary Markdown
  authoring (headings, lists, blockquotes, emphasis, links, images, tables,
  code) plus Gutterpress-specific authoring: layout markers render as
  recognizable chips instead of raw `@` syntax, and project-plugin regions
  render through the plugin's own output, with a two-state
  (inactive/active) design and a source-editor fallback wherever the editor
  cannot prove a region is safely editable.
- **Undo and redo on the page.** Unlocked, Ctrl+Z takes back the last edit
  and Ctrl+Y (or Ctrl+Shift+Z; Cmd on macOS) puts it back, one chapter at a
  time, with a run of typing as one step; the desktop host keeps the history
  (`packages/desktop/src/lib/editor-host/desktop-document-host.ts`) and
  undoes by replaying each edit's inverse through the same bounded
  `applyEdit`, so the source stays exact.
- **A new, Experimental VS Code extension**, `@dimm-city/gutterpress-vscode`
  (published separately from `gutterpress`). It registers an optional
  custom text editor — never the default for `.md` files — built on the
  same shared editor package, with Build/Preview/Open Source commands and
  workspace-trust-gated plugin execution. See `docs/vscode-extension.md`.
  Because `@vscode/markdown-editor` has no generic hook for a custom block
  view, the rich surface runs on a small internal fork,
  `packages/vscode-markdown-editor` — nine additive patches, 29 hunks
  against the pinned upstream version (0.0.2-87), documented hunk-by-hunk
  with a removal trigger per patch and a re-pin trigger in `PATCHES.md`.
  See `docs/adr/0014-shared-editor-package-and-fork.md`.
- **New public subpath exports**: `gutterpress/plugins` (the same plugin
  loader the CLI's build and preview pipeline uses, for any host) and
  `gutterpress/viewer` (the paged layout engine for a browser);
  `gutterpress/render` gained the projection surface the shared editor
  consumes (`createEditorProjection`, `PROJECTION_SCHEMA_VERSION`,
  `inlineSourceMetaOf`, `sourceTokenOccurrenceAt` and their types).
- **Desktop host routes** for the editor, on the app's route-first
  architecture (root `CLAUDE.md` §8): `POST /api/editor/projection`,
  `GET /api/editor/asset/[name]`, `GET /api/editor/project-file/[...path]`
  and `POST /api/log/renderer-error`; the preview protocol gains
  `getChapters()` (v9). See `docs/architecture/source-first-editor.md`.

## What did not ship from the editor program

The editor branch also carried an Electron single-IPC transport (ADR
0016), feature-owned capability modules in place of the `api` wrapper (ADR
0017), and a read-only preview with in-preview editing deleted (ADR 0013).
Main had meanwhile settled the same questions the other way — routes as
the default host seam, in-place block editing in the preview (ADR 0009),
and the PWA code removed in 0.11.11 — and main's answers stand. Those three
ADRs are not part of this release; the editor is wired onto main's routes
instead. The program's own history, including those phases, remains under
`docs/plans/source-first-editor/`.

## Known limitations

Carried honestly, not glossed over:

- **The D13 performance budget is not met.** The plan's target: repeated
  ordinary typing in a 250 KiB document keeps p95 edit-to-paint under
  100 ms after warm-up. Two corrections to the earlier record first:
  `test:perf` is not a CI job (`ci.yml` runs only `test` and
  `test:browser` for `packages/editor`), so no "CI reference runner"
  numbers exist and every figure here is a sandbox figure; and until
  2026-09-28 the benchmark typed at character ~937 of a 256,018-character
  document (a bare `End` after a click lands near the start) while
  claiming end-of-document typing - so the vendored fix, Patch 2
  (`SFE-P3f`), whose improved path is end-of-document typing, was never
  exercised by the gate. With the benchmark fixed (`Control+End`, sample
  reset after navigation - `packages/editor/tests/perf/support/drive.ts`),
  the in-repo `bun run test:perf` run of 2026-09-28 (09:50 UTC, commit
  f5c7926 plus that fix, sandbox, n=60 per size) measures 250 KiB p95 at
  **~280-305 ms** end-of-document (304.1 and 279.4 ms over two runs)
  against the **~554-632 ms** the near-start shape measured (the pre-patch
  band in `p3d-sweep-audit.md`; 560-577 ms patched, the shape Patch 2
  cannot help); both are over the 100 ms budget. The other sizes: 25 KiB
  p95 36.3 ms (within budget), 100 KiB 121.8 ms, 1 MiB **~1.16 s**. The
  residual scales at roughly 1 ms per KiB (250 KiB p50 ~205 ms, 1 MiB p50
  ~890 ms) and lies outside `_renderAutorun`: it is present with
  `_publishMeasurements` fully disabled (`PATCHES.md`'s prototype, 250 KiB
  p50 255.2 ms). Upstream `@vscode/markdown-editor@0.0.2-111` (published
  2026-09-28, gitHead 3fd578f) leaves `_publishMeasurements`
  (`dist/index.js` 7046-7085), the non-incremental `_renderAutorun` call
  (7035) and the full-document `editContext.updateText` mirror (7006)
  unchanged, so Patch 2's removal trigger is not met and a re-pin is not a
  performance fix. Two ordered follow-ups remain in
  `packages/vscode-markdown-editor/PATCHES.md` and the SFE-P3f close-out:
  implement the delta-translation variant so mid-document typing also
  reuses cached geometry; then re-profile the remaining residual (an
  EditContext input-path cost that is located but not yet proven as the
  cause). The paged editor remains fully usable for ordinary
  chapter-length documents; this budget governs sustained typing in large
  (250 KiB+) files specifically.
- **Three interaction shapes are deliberately not implemented, not
  missing by accident**: paste into the rich editor is plain-text-only (no
  rich-paste formatting yet); block movement has no pointer-drag path
  (keyboard-driven move commands exist); there is no slash-command menu in
  the paged editor outside the desktop's existing toolbar. These were
  evaluated and pinned as acceptable for `0.12.0`'s Experimental release
  rather than deferred by omission.
- **A text block in locked Read is not double-click-editable.** The
  paged editor's double-click handler (`onRichDoubleClick` in
  `packages/desktop/src/routes/+page.svelte`) opens image properties for an
  `<img>` only; on text it does nothing. Unlock first (the pill, or
  right-click > Unlock to edit, which places the caret in that block).
- **Image drop and paste do not import or insert.** Dropping an image file
  from the OS or pasting a clipboard image does not import or insert it in
  either mode; an SVG dropped on the source editor is inserted as its XML
  text (CodeMirror 6.43's upstream default, not Gutterpress code). The
  supported path is Media > Add images, then Insert (or tile drag into the
  source editor).
- **A few plugin-heavy layouts fail closed to source-only editing in the
  paged editor** rather than offering rich editing: an image or link inside a GFM
  table cell with an escaped `|` refuses editing for the whole row, and an
  image inside a raw HTML block refuses. Both are intentional fail-closed
  behavior (an ambiguous case falls back to source rather than guessing),
  not silent data loss.
- **Real-VS-Code activation is a recorded deviation, not a gap in the
  extension itself.** A bounded `@vscode/test-electron` attempt was made
  and failed on a network policy denial in this sandbox (`downloadAndUnzipVSCode`
  cannot reach `update.code.visualstudio.com`; exact command and failure
  recorded in `docs/plans/source-first-editor/runs/SFE-P3c.md`'s
  "Deviations and evidence" section), and the resulting dead launcher
  scaffold was removed rather than left in the tree unused. The extension's
  evidence for this release is its harness test suite (228 unit + 34
  browser tests, run against a fidelity mock —
  `packages/vscode-extension/tests/support/fidelity-vscode.ts` — with real
  `TextDocument`/`WorkspaceEdit` semantics computed from actual text
  content, not hand-written per-test return values) plus a real-Node
  module-load test proving the built `dist/extension.js` actually loads
  (an earlier build did not: bundling `gutterpress` in dragged a
  CJS-incompatible import along with it). The first environment with
  network access to the VS Code download host should run a real
  `@vscode/test-electron` pass before this extension moves past
  Experimental.
- **Packaged-asar smoke: closed this release.** Every prior run's
  packaged-build evidence ran Electron **unpackaged** (`out/main/main.js`
  directly, `app.isPackaged === false`), with the asar-serving code path in
  `electron/app-protocol.ts` proven only by a unit test stubbing
  `process.resourcesPath`. The P7 sweep
  (`docs/plans/source-first-editor/p7-sweeps.md`) drove the real thing: an
  `electron-builder --linux dir` build produced `app.asar` (8,856 entries;
  renderer build, main, and preload all inside, zero server-bundle
  markers), and the packaged binary launched headlessly to first paint with
  the renderer served over `app://` from the asar and no fatal log lines.
  Windows/macOS packaged smokes remain CI-runner work.

## Post-merge review (main synced 2026-10-11)

`release/0.12.0` was brought up to `main` at 0.11.17-alpha.4 (43 commits:
0.11.15, 0.11.16 and the 0.11.17 alphas). Main won every conflict; the
editor-only additions were kept. These are the places where the two lines
touched the same code and a reviewer should read the result, not the diff:

- **Viewer engine (`packages/cli/src/engine/viewer/fragment.ts`,
  `decorate.ts`).** Main added signature padding (`padToSignature`,
  `paddedPageIndices`, `ctx.padded`) and the missing-image placeholder so
  the preview's page count matches the PDF; the release branch added the
  per-pass computed-style read cache (`withLayoutReadCache`), the
  xref-stylesheet write-only-on-change, and the editor's `pageOffset` on
  `data-page`. Both now run inside the cached pass. Check: padded pages in
  the preview, folios across chapters in the unlocked book, and the
  native parity gate (`native-parity-gate.ts`) with an empty allowlist.
- **`@columns` and the paged editor.** Main's core-declared `@columns`
  marker reaches the editor as a `layout_component_open` token (kind
  `plugin-marker`) with a `div.gp-columns.gp-columns-N` wrapper, so the
  unlocked book lays its content out in columns through the same
  container grouping a plugin marker uses. `CORE_MARKER_LINE_RE` in
  `editor-projection.ts` now includes core-declared names, so a plugin
  region's recovered range that swallows `@columns`/`@end-columns` is
  refused like one that swallows `@section`. Check: unlock the user guide
  (chapter 2 uses `@columns`), the chip the opener gets, and the Two
  columns toolbar item in both editors (`descriptorForLayoutBlock` now
  inserts `@columns 2`).
- **Section markers (`section: true`), self-closing markers and the
  component token contract (#340, #344).** The projection maps
  `layout_section_open` to a section regardless of which marker produced
  it, and a self-closing marker produces an open/close pair with no
  content. Neither has an editor-side test yet. Check: a plugin book
  using both, unlocked, for chips, wrappers and projection notices.
- **The glued-marker warning (`marker_glued`) against main's component
  `validate()` tests.** Main's fixtures glue markers to their content;
  the release branch warns about exactly that. The tests now filter the
  warning out (`markers.test.ts`, `layout-markers.test.ts`), which keeps
  both behaviours. Decide whether the warning should stay a warning for
  books that have always written markers that way.
- **Markdown renderer and marker parser (`renderer.ts`, `markers.js`).**
  Main's declared-marker registry (`buildDeclaredMarkerRegistry`, aliases,
  variants, `validate`) auto-merged with the release branch's
  `parseMarkerLine(line, declaredWords, { allowUnknownKinds })`,
  `markerElementAttributes` and the exported `KNOWN_KINDS`. Tests pass;
  read the merged `parseMarkerLine` once end to end.
- **Desktop page (`+page.svelte`) and toolbars.** Main replaced the
  loading overlay with `ActivityGate`/`ActivityIndicator`, moved the save
  indicator back to the status bar, added `components` to the source
  editor and regrouped the status bar; the release branch wires the paged
  editor, the lock pill and the book page navigation into the same file.
  The rich-mode `EditorToolbar` instance was realigned to main's props.
  `PreviewToolbar` is now a three-track grid with the zoom menu and the
  lock pill in the right track. Check narrow panes (the 420/340/270px
  container fallbacks) with the pill present.
- **Preview protocol.** Main stayed at version 8 and added a `fit`
  argument to `setZoom`; the release branch is at 9 (`getChapters()`).
  No collision, but the desktop's `preview-client.ts` and the shell were
  merged from both sides.
- **Extension install/restore and the editor projection route.** Main's
  "extensions out of git, restored on open" (#345) changes when a plugin's
  vendored copy exists; `/api/editor/projection` loads plugins through
  the same loader and reports `pluginErrors`. The host test's expected
  needs-install wording follows main's loader. Check: unlock a book whose
  extensions are not yet restored.
- **Test infrastructure.** Bun runs the desktop tests in one process in
  filesystem order, and the files shim Svelte's `$state` rune with `??=`;
  main's `activity-gate.test.ts` needed `$state.raw` and failed whenever a
  plain shim ran first. Its shim now adds `raw` to whatever is installed.
  The generated viewer bundle (`src/assets/engine/gutterpress-viewer.js`)
  was rebuilt from the merged sources, not merged by hand.
- **Not re-verified here:** the website/docs move (`website/`, `site/`
  removed), package-manager assets, and the CLI `ext` commands - main
  owns them and the merge took main's versions untouched.

### Outcome of the review

Each area above was read end to end and driven in the built app. What it
found and what changed:

- **Viewer engine.** One chapter's layout swept the whole document: in the
  unlocked book it removed other chapters' recto spacers and undid their
  overflow clipping. Every document-wide query in `paginate`/`relayout`
  and `decorate` is now scoped to `opts.root`. Blank recto pages and the
  `:first`/`:left`/`:right` page selectors now follow book parity
  (`LayoutOptions.pageOffset`, re-paginating when the offset's parity
  flips), and `counter(pages)` counts the book (`bookPages`). Signature
  padding is not applied in the unlocked book (see Open questions).
- **`@columns`, section and self-closing markers.** The editor classified
  declared markers without the project's vocabulary. The projection now
  carries `declaredMarkers`, and the provider uses it. A section marker
  wraps like `@section` with its declared classes, a self-closing marker is
  one generated element with nothing wrapped, `@page` above `@columns`
  holds the wrapper, and text glued under `@columns` lands inside it.
  Pages repeat their chapter's label, a stray `@continue` and `@end-…`
  prose stay as printed, and a fenced code block showing a marker is no
  longer refused as a swallowed marker. Covered by new tests in
  `provider.test.ts`, `editor-projection-declared.test.ts` and
  `editor-projection-plugins.test.ts`.
- **Glued markers and the parser.** `@end-columns` above `@page` was
  reported as glued (the boundary check ignored declared words), and core's
  `gp_component_validate` rule was taken for a plugin rule by the
  plugin-origin bracket. Both fixed with tests. The section and two-column
  templates, and marker-pair completions, now leave the caret on a line of
  its own.
- **Desktop page and toolbars.** Fixed: the lock pill overlapping page
  navigation in panes 420px and narrower, a book switch while unlocked
  (stayed unlocked, briefly mounted the old book's chapters, two uncaught
  errors), Insert snippet doing nothing on the page, the Problems badge
  opening nothing on the page, a plugin-load failure toasting once per
  chapter and edit, and the "Updating preview" pill over the formatting
  bar. A chapter that cannot be read no longer stops the rest of the book
  mounting.
- **Extension restore and the projection route.** The route does not
  restore; an author cannot unlock before the open (and its restore)
  finishes, so this holds. The editor's book-CSS cache only stamped the
  top-level stylesheets, so an edited `@import`ed partial or a replaced
  font left the page stale; it now stamps the whole dependency closure
  (`collectStyleDependencies`, now exported).
- **Test infrastructure.** Every desktop test file passes alone, in
  reverse and in random order.

**Decided with the product owner** (2026-10-11) and done:

- **Signature padding.** The unlocked book pads like the preview. The
  projection route returns the manifest's `print` padding; BookSurface
  computes the padding from the whole book's content pages and gives it
  to the last chapter (`LayoutOptions.padPages`). Padded sheets carry
  `data-padded`, and the editor/preview parity gate now checks the
  book's total with padding as well as each chapter's own pages.
- **Cross-chapter references.** Each chapter's decoration reports the page
  of a target it holds (`DecorationApi.pageOfTarget`) and accepts the
  pages of targets it does not (`setExternalTargets`). BookSurface
  resolves every in-book link against the chapter that holds its target.
  The editor now applies a `{...}` written straight after a link,
  emphasis, strong, code or image to that element, as markdown-it-attrs
  does (`decorateInlineAttrs`). The parity gate compares every in-book
  link's generated text.
- **`marker_glued` stays a warning.** The 36 glued lines in fenced
  examples (the design-guide example, the theme and plugin template
  READMEs, `docs/contextual-cascade-principle.md`) and the plugin
  template's doc comment now put a blank line around every marker.

Verified after these fixes: CLI 2640 pass (the Chromium-launch tests need
Chromium 148 and cannot run here; CI runs them and the parity gate),
desktop 5898, editor 3053 plus every browser suite, VS Code extension 226,
svelte-check, eslint and the Electron typecheck. In the built app the
review's own probes now pass: toolbar widths 260-1600px, a book switch
while unlocked, snippet insert, Problems, plugin-load toasts. So do the
recto, cross-reference, page-navigation, chip-editing and typing drives.

Verified on the merged tree: library build and purity gates; CLI (2631
tests, the one Chromium-launch test skipped here), desktop (5899),
editor (3053 plus the browser suites), VS Code extension (226); svelte-check,
eslint and the Electron typecheck; the eight behaviour drives; the
editor/preview parity gate; and in the built app, unlock on the user guide
(now 83 pages with `@columns`), page navigation, chip editing, Enter to
confirm a marker and typing at ~20 ms a keystroke.

## Upgrade notes

- **Nothing changes for readers.** Read opens locked, on the same preview
  as before; the lock pill is offered to authors only.
- **No project file format, manifest, CLI, build, or publish behavior
  changes in this release.** Everything above is editor and desktop-app
  architecture; a project that built and previewed correctly under 0.10.2
  builds and previews identically under 0.12.0. The public `gutterpress`
  and `gutterpress/api` exports are unchanged; `gutterpress/render` gained
  the projection surface the shared editor consumes (`createEditorProjection`,
  `PROJECTION_SCHEMA_VERSION`, `inlineSourceMetaOf`, `sourceTokenOccurrenceAt`
  and their types). The markdown-it plugin API contract for plugin authors
  is unchanged (plugins
  remain ordinary `(md, options) => void` markdown-it plugins — no new
  Gutterpress-specific plugin API was introduced for rich-mode support).
- **`@dimm-city/gutterpress-editor` and the VS Code extension are
  Experimental for `0.12.0`.** Their identifiers, commands, and internal
  contracts may change without the deprecation cycle a stable Gutterpress
  surface would owe you. If you don't unlock the paged editor or use the
  VS Code extension, nothing in your workflow changes.
- **No user-data migration.** Nothing about your project's files, version
  history, or sync state changes as part of upgrading.
